# The Validation subsystem — how it works, and how we know it works

Written 2026-10-08 for Jacob. Everything here is checked against the code
as of this date; counts are from the repo.

## 0. One paragraph

A DDR3 memory controller (11 blocks) is generated by the Frontend from a
machine-readable spec. Validation never trusts the generator: it derives
*what the design must do* from the spec alone, simulates the generated RTL
in Cadence Xcelium on Olympus through 22 integration "paths" (chains of
blocks with real stimulus), captures every transaction on 26 internal and
external streams, and judges the captured traces offline in Python against
reference models, legality rules, and generated SystemVerilog assertions.
Every disagreement becomes a *finding* with an owner block, a spec
reference, expected vs actual, a source anchor and a reproduction command,
and goes back to the Frontend's repair agents through one fixed handoff
directory. The verification itself is held to the same standard as the
design: seeded faults must be caught, a known-good open-source controller
must pass, two independently generated models must agree, formal must
prove what simulation cannot reach, and a ledger records which of the 57
checks have both kinds of evidence.

## 1. The three subsystems and the loop (`flow.py`)

```
English/preset ─► Frontend microarch agent + compiler ─► generated_spec.json
                                   │
                    Validation: validate_spec_stage (schema, JESD79-3, register map, intake gaps)
                                   │ PASS
                    Frontend phase pipelines 1..4 (+ generate_top) ─► drop/PHASE{1..4}RTL, TOPRTL
                                   │
                    Validation: validate_drop (resolve → review → regenerate checkers → simulate paths → judge → findings)
                                   │ FAIL ──► Frontend phase validation agents (--findings) ─► regenerate ─► validate again (cap 4)
                                   │ PASS
                    Backend: RTL → GDSII (ORFS in Docker); its findings come back the same way (cap 2)
                                   │ PASS
                    Validation: the backend's per-block netlists re-run through the same paths (run_path --netlist)
```

`flow.py` at the repo root drives all of it through each subsystem's own
CLI, non-interactively, one directory per run (`runs/<id>/`), with
`RUN_STATE.json` so a halted run resumes. Halts are explicit: a failed spec
review, a phase whose repair agent doesn't exist (3, 4), caps reached, a
block the run generated that could not be judged.

## 2. The spec is the only source of truth

`Spec/llmmc_microarchitecturespec_filled.json` (golden DDR3-1600K) or the
Frontend's compiled `generated_spec.json` (e.g. DDR3-1333 x8). Validation
loads exactly one spec per run (`VALIDATION_SPEC`), and every checker,
assertion, register model, coverage point and legality rule is *derived*
from it at run time. Nothing is tuned to the golden design: the same
infrastructure validated the compiled 1333 spec's Phase-1 blocks with zero
code changes, and the seeded faults were still caught by checkers built
from that spec (`SEMESTER_PLAN.md`, 2026-10-01).

Before any RTL exists, `spec/validate_spec_stage.py` reviews the spec:
schema (required sections, types, enums, patterns), JESD79-3 conformance
(`jedec/jedec_ddr3_rules.json`, 25 rules recomputed from the numbers; the
spec's own "[check]" claims are re-derived, never trusted), register-map
self-consistency (offsets, bit ranges, reset values, TIMING_* resets equal
the derived nCK values), and 12 *intake rules*
(`spec/completeness_rules.json`) — questions the spec leaves open (DM
polarity, unmapped CSR reads, tMRD/tMOD…). Gaps are advisory; validation
judges under a pinned convention and the question is routed to a human or
the synthesis agent.

## 3. The data that describes the design (no RTL knowledge in code)

- `txn/interface_catalog.json` — 26 **streams**: for each, the block that
  owns it, the ports that carry each field, the qualifier (when a
  transaction happens), command encodings, roles (request/response),
  `derives_from` (how a response relates to its request), don't-care
  fields, sampling discipline, model guidance.
- `txn/schema_gen.py` → `txn/generated/schemas.json`: the catalog resolved
  against the drop's **manifests** (port names and widths the Frontend
  stamps on every block), so a port rename or width change is caught at
  intake, not in a waveform.
- `structural/integration_map_gen.py` → `integration_map.json`: how the 11
  blocks connect, derived from the manifests' `source` declarations plus a
  small set of declared glue; it refuses width-inconsistent edges and files
  them.
- `spec/path_definitions.json` — the 22 **paths**: which blocks, which
  stimulus, which check strategy (exact / composed / invariant / observe).
- `structural/rtl_drop.py` — the **resolver**: where RTL and manifests come
  from (declared roots only, phase directories preferred, differing copies
  refused), the content-hash **drop id**, each block's spec revision.
- `spec/spec_identity.py` — the **spec id**: sha256 of the spec's canonical
  JSON. A revision is a name; the id says whether two files are the same
  spec. `validate_drop.py` judges against the spec the drop ships when it
  carries a known revision with different content (and files
  `SPEC_REVISION_REUSED`), and every record that names a revision carries
  the id beside it (handoff, findings, model provenance).

## 4. What runs on the simulator (`tools/run_path.py`)

For one path:

1. `structural/chain_harness_gen.py` writes `chain_harness.sv`: the path's
   blocks instantiated and wired per the map (plus the support closure the
   map declares and a behavioural DRAM stub behind the pins), inputs no
   block drives tied as the map says, a driver module attached to the entry
   stream. A `standalone` path (one block, for phase-by-phase drops) ties
   its cut edges from declared `standalone_ties`.
2. `sequences/` produce the **stimulus**: constrained-random
   (`closure/random_v2.py`: address profiles, bank/row revisits, read/write
   mix), or directed generators (register walk, status poll, refresh
   stress, bursts). The sequence is a JSON contract
   (`sequence_contract.py`) rendered into `seq_driver.sv` by
   `driver_gen.py`, which knows each stream's handshake (valid-style, or
   Wishbone B4 pipelined: hold while stalled, drop `stb` on accept, wait for
   `ack`).
3. `txn/monitor_gen.py` writes one **passive monitor** per stream, bound
   into the block with `bind`; each prints a `TXN` line per transaction
   (post-NBA sampling for outputs, pre-NBA for inputs the block samples).
4. `sva/sva_gen.py` writes **assertions** from `sva/sva_rules.json` and the
   spec's timing: 13 on the DDR command pins (tRCD, tRP, tRAS, tRRD, tFAW,
   tWR, tWTR, tRTP, tCCD, tRFC, tREFI, bank-state PROTO rules), 5 on the
   init sequence (MRS order, ZQCL last, tZQinit, init_done), 2 on
   calibration ordering — bound into the blocks.
5. `sva/coverage_gen.py`, `block_coverage_gen.py` write covergroups
   matching the **verification plan** (`vplan/vplan.json`, 39 items
   generated from the spec).
6. Everything is uploaded, `xrun` runs on Olympus (via `agents/sim_runner.py`
   over SSH/srun), the log comes back.
7. `txn/trace_extract.py` turns `TXN` lines into `observed.jsonl`.
8. **Judging** (`txn/scoreboard.py`), offline in Python, per stage of the
   path:
   - *exact* stages: a **predictor** (reference model) consumes the stage's
     input transactions and predicts its outputs; the scoreboard aligns
     predicted vs observed per stream and reports missing / unexpected /
     value mismatches (don't-care fields masked).
   - *invariant* stages and path-level checkers: a **legality checker**
     observes all streams and files violations of named rules
     (`gates/stage_invariant_rules.json`: 34 rules across 9 stages, e.g.
     SCHED_001 no dropped request, PROTO_001 no CAS to an idle bank,
     REF_001 refresh postpone budget).
   - fired assertions from the log are folded in: an assertion bound to a
     stage's block fails that stage; a support block's assertion fails the
     path.
9. A report per path; `validate_drop.py` orchestrates all paths,
   coverage rollup (IMC), findings, drop comparison, snapshot, cockpit.

## 5. The split that makes LLM use safe

Reference models and checkers are generated by an LLM (`agents/predictor_agent.py`,
Opus) from the spec and schemas only — never from the RTL. They are
**accepted only by a gate** (`gates/predictor_gates.py`), which is
deterministic code that composes its expectations from the same spec:

- `RegisterMapGate` — reset readback, RW/RO/RW1C/WO semantics, register
  independence, width masking, non-vacuity, configuration broadcasts.
- `BusBridgeGate` — request translation, constant bits, complementary
  drive patterns, completion semantics.
- `StageInvariantGate` — every rule's violating trace must fire, every
  legal trace (and named legal variants that pin conventions) must not.
- `LegalityCheckerGate` — command-stream rules.

A model that fails is re-prompted with the gate's rejection; a scope no
gate covers is refused ("UNGATED"). The gates themselves are
mutation-tested in `tests/` (a model with a deliberate wrong value, a
silent broadcast, a swapped field mapping must be rejected). Everything
deterministic — monitors, SVA, harness, scoreboard, vplan, coverage, the
resolver, the gates, the findings pipeline — is generated or written by
code and tested (24 test files).

## 6. Findings and the loop back

`findings/emit_findings.py` turns a drop's reports into **findings v2**:
one record per (owner block, check), with severity, confidence
(`confirmed` = model-free evidence: assertion, rule, structural, repair;
`observed` = a predictor disagreed), the spec requirement, expected/actual,
occurrences and paths, source anchors (file/line/signal in the drop),
mechanism, a repro command, history across drops (first seen, introduced
in, resolved). Owners come from `rule_owners` tables (a spacing violation
is bound to cmd_gen's pins but owned by the scheduler). `retry_adapter.py`
renders them in the Frontend's `retry_instructions.json` shape and publishes
everything to `findings/outbox/current/` with a `HANDOFF.json` naming the
drop id and spec revision (`HANDOFF_CONTRACT.md`). Structural findings
(spec mismatch, width mismatch, manifest audit), formal counterexamples and
repair-proven defects join the same stream; backend STA findings arrive in
the same envelope and are routed the same way.

## 7. How the validation is validated

This is the part a verification engineer is judged on.

1. **Seeded faults** (`faults/`): 23 catalogued RTL mutations across all 11
   blocks (stuck bank field, ACT encoded as PRE, tRAS short, refresh never
   requested, RW1C settable, WE inverted, skipped MR2, tZQinit short, CAS
   without ACTIVATE…). Each is applied to a copy of the drop, run through
   its paths, and scored differentially against the clean baseline: the
   fault must produce *new* evidence (a specific check) and the blame must
   land on the mutated block (via `rule_owners`). 23/23 killed, blame
   correct, 0 masked. Faults that an open design defect would hide are
   reported apart, never counted.
2. **Known-good design** (`refdesigns/uberddr3/`): the open-source UberDDR3
   controller, under our monitors, SVA and path checkers — 0 assertion
   failures over 15,946 DDR commands, 0 checker violations over 9,216
   requests, 0 data-integrity mismatches. Two checkers that fired on it were
   wrong and were fixed (speculative ACTIVATE is legal; precharge-all is
   not a bank precharge). This is the false-positive floor.
3. **Second opinions** (`agreement/`): every predictor and checker has an
   independently generated twin; `model_agreement.py` replays all traces
   through both and reports substantive disagreements (different violation
   counts; witness differences are attribution). As of today every checker
   scope agrees on every trace; the only predictor disagreement left is
   data_path, which is a spec gap (DM polarity).
4. **Oracle agreement**: for rules with three oracles (Python rule, SVA
   assertion, formal), they are compared run by run.
5. **Formal** (`tools/run_formal.py`, JasperGold): the generated SVA proven
   on a synthesizable top; command path 4 proven / 8 counterexamples filed
   as findings; init/calibration 6/7 proven (one property is graded by
   simulation; the counterexample under the wait-counter abstraction is
   spurious and marked so).
6. **Repairs** (`repairs/`): minimal source fixes applied to a *copy* of
   the drop; a finding whose repair silences exactly the named checks and
   nothing else is `confirmed` with the fix as its anchor (R01–R03 on the
   scheduler/bank_tracker).
7. **Determinism**: the same drop validated twice yields identical findings
   (`compare_drops.py --strict`).
8. **Models re-graded per drop**: every accepted predictor/checker is run
   through its gate again under the spec being judged against
   (`validate_drop.py` step 3a) and regenerated by the agent when the gate
   rejects it; its provenance records the spec id it last passed under. A
   model accepted under an earlier spec is not evidence about a drop
   generated from a later one (2026-10-08: a 3-bit status-field model under
   a 4-bit spec, same revision string).
9. **Gate mutation tests, resolver tests, flow tests**: `tests/` (25 files)
   pin every rule the harness relies on, including the ones learned the
   hard way (sample point, witness attribution, drop-id coverage).
9. **The ledger** (`agreement/check_ledger.py` → `reports/check_ledger.json`):
   57 checks; a check is *closed* only with evidence it **fires** on a wrong
   design (seeded fault, repair, formal cex) and stays **silent** on a right
   one (known-good, proof, repair baseline). Today: 50 closed, 6 silent-only,
   1 fires-only, 0 false positives.
10. **Gate-level**: the backend's netlists through the same paths; both
    available netlists pass, and the exercise found two defects in our own
    checkers (a sampling race, a verdict that ignored fired assertions).

The pattern throughout: when a check fires, the first question is "is it
the design or us?", and twice the answer was us (the Wishbone driver, the
monitor sample point, the SVA counters on gate-level flops, the verdict).
Each time the lesson became a test or a catalog field, not a note.

## 8. Coverage and sign-off

Code coverage (IMC) ~75% on the current drop; vplan 9/39 items fully
covered, 12 partial; `SIGNOFF.md` defines verdict levels, per-block targets,
exclusion codes (E-DEAD requires a formal unreachability or a cited
constant), a waiver policy (named human approver), the formal bar, the
known-good bar, the gate-level rule, and what a phase-partial drop may
claim.

## 9. How this compares with industry UVM

What it *is*: a layered, transaction-level, spec-driven, coverage- and
assertion-backed environment in the UVM mould — passive monitors emitting
transactions, a scoreboard comparing against reference models, sequences
rendered by drivers with handshake-aware BFM behaviour, functional
coverage tied to a verification plan, SVA, formal, and regression
(vManager). The *discipline* matches industry practice and in some places
exceeds it (mutation/fault injection, a known-good design, independent
model generation, a ledger of two-sided evidence — most teams do none of
the first three systematically).

What it is *not*: the UVM class library. Concretely:

| UVM element | here |
|---|---|
| `uvm_component` hierarchy, phases, factory, `config_db` | generated flat SV harness; composition is data (map, paths), not class overrides |
| `uvm_driver` / `uvm_sequencer` / `uvm_sequence` | sequences are JSON contracts generated in Python and rendered to a driver module; no reactive sequences, no virtual sequencer, no in-sim sequence library |
| `uvm_monitor` + TLM analysis ports | generated passive monitors printing `TXN` lines; the "analysis port" is the log → trace file |
| `uvm_scoreboard` in-sim | Python scoreboard **offline**, after the run; a mismatch is found minutes, not cycles, after it happens; no in-sim end-of-test checks |
| reference model in SV/C++ via DPI | Python models generated by an LLM and accepted by gates |
| `uvm_reg` / RAL | a Python register model derived from the spec (`refmodel/spec_register_model.py`) with the same intent (reset, access types, mirrors), not RAL's frontdoor/backdoor API |
| SV constrained-random (`rand`, `constraint`) | Python generators with profiles; no constraint solver; "constrained" means generated within spec ranges and shaped by profiles |
| `uvm_report_server`, severities | findings v2 (owner, confidence, anchors, history) — richer, but a different vocabulary |
| coverage-driven closure (`covergroup` + merge + rank) | SV covergroups generated from the vplan, IMC rollup; closure is manual/profile-driven, no ranking |
| objections / end-of-test | settle windows per path |

Where a reviewer would push: (1) in-sim scoreboards for immediate failure
and shorter debug loops; (2) reactive stimulus (drive based on DUT state,
e.g. wait for init_done, back-pressure-aware sequences) — our drivers only
react to the handshake; (3) a constraint solver for genuine
constrained-random with coverage feedback; (4) end-to-end data integrity on
the full controller (we have it only on UberDDR3 and partially on
path_18); (5) a RAL-style register layer the sequences use directly. None
of these change the verdicts the system produces today; they change how
fast a new bug is localised and how much of the state space random
stimulus reaches.

Where this is *ahead* of a typical UVM bench: the checks are derived from a
machine-readable spec and regenerate when the spec changes (a UVM bench is
hand-written per design); the checkers' correctness is measured (faults,
known-good, twins, ledger) rather than assumed; and every result is a
routable, machine-readable finding with an owner.
